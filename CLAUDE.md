## 1. Project Overview

End-to-end pipeline for detecting and quantifying lichen (*địa y*) on cinnamon tree trunks (*Cinnamomum cassia*, quế) using iPhone LiDAR scans (patched Stray Scanner app). Input: raw scan data (RGB video, depth maps, IMU, odometry, GPS metadata). Output: colored 3D mesh with lichen labeled by type and spatial orientation (upslope/downslope), with coverage statistics in cm² and %.

- **Institution:** VinUniversity, Hanoi
- **Scale:** 500–1000 trees across 2–3 field sites (currently ~90 trees actively processed)
- **Accuracy — [MEASURED Sep 21 2026, and the original claim is wrong].** The original docs claimed ~70% on clean samples (HSV adaptive thresholding) and this file has carried it flagged as never independently re-verified. It is now verified against hand labels on `cay_0004_1805` (§12 item 19): the active detector scores **precision 6.3%, recall 0.2%, F1 0.5%** — it finds 10 of 3,271 hand-marked lichen points, and reports 0.7% coverage where the annotator marked 17.9%. **Do not quote the 70% figure anywhere.** A label-fitted replacement measures **F1 41.3% on trees it has never seen** (three trees, leave-one-out — §12 item 20) against the shipped detector's 9.5% on the same test. **It is not in the pipeline and must not be put there yet: that F1 measures *where* lichen is on a trunk, and the same model's *per-tree total* is anti-correlated with the hand labels (§12 item 21).** See §9 and §12 items 4, 16, 18, 19, 20, 21.

> ⚠️ **Reconciliation note:** This file merges the original project CLAUDE.md with findings from an extended hands-on debugging session (Aug–Sep 2026). Where the two disagree, the debugging-session findings are marked **[VERIFIED]** because they were confirmed against the actual GitHub repo content and actual runtime behavior on the working machine. Anything only in the original docs and never touched during that session is marked **[UNVERIFIED / other branch]**.

On Sep 20 2026 it turned out there is no fresh checkout to re-apply to: the local pack was corrupt (199 `fsck` errors) and the GitHub remote is unreachable (no SSH key). Git history now does that job — see §11 for the `.gitignore` failure that had been silently preventing every commit.
>
> **Going forward:** edit the numbered scripts directly and commit. Keep changes small and separately committed so a single one can be reverted. The two rules below (pure ASCII, UTF-8 subprocess env) still apply to all code in this repo.
- Patch scripts and their string literals must be **pure ASCII** (no Vietnamese diacritics) — Windows console defaults to `cp1252`, which cannot encode Vietnamese characters and breaks both `pip` output and any script `print()` of a diacritic path.
- Any `subprocess` call to a child script must set `env["PYTHONIOENCODING"]="utf-8"` and `env["PYTHONUTF8"]="1"` — required because scan folder names are user-provided and may contain Vietnamese diacritics (e.g. `Tây-trà-bồng-2`).
- Core algorithms this project standardizes on: **RANSAC** (ground-plane removal), **DBSCAN** (`o3d`'s `cluster_dbscan`, keep-largest-cluster), **`scipy.spatial.cKDTree`** (nearest-neighbor queries — camera-trajectory anchoring, mesh↔point-cloud color transfer). Do not reintroduce mean/median-center-based cropping (see `04_auto_clean.py` — this is exactly the bug pattern already fixed once, §9).

### Change log by script (historical patch names kept as identifiers)

**`05_trunk_isolation.py`** (called at pipeline step 3):
1. `patch_trunk_isolation.py` — filter NaN/Inf/|coord|>50m before any computation (guards against `~1e260`-magnitude garbage points from corrupted PLY writes)
2. `patch_trunk_isolation_downsample.py` — voxel-downsample to 1cm if >1M points (prevents RAM-exhaustion crashes, e.g. `STATUS_STACK_BUFFER_OVERRUN` seen on 11M-point clouds on an 8GB machine)
3. `patch_trunk_isolation_kdtree_anchor.py` — **[RESTORED Sep 2026]** was documented here as "current" but confirmed **absent from disk** (repo-wide search found no such file) — almost certainly lost in the drive-corruption incident (§4). Rewritten from this doc's own description: anchor to camera trajectory using `cKDTree` over *all* camera positions from `odometry.csv`, radius=1.0m to nearest camera pose (not a single averaged center). Replaces the `camera_anchor_z` block that was actually present on disk.
   - ~~`patch_trunk_isolation_camera_anchor.py`~~ (XY-only, mean-center + fixed radius) — superseded
   - ~~`patch_trunk_isolation_camera_anchor_z.py`~~ (XY mean-center + Z-range) — superseded; this was the variant actually on disk until the Sep 2026 restoration above
   - Rationale for the KDTree version: two independent real-world failures were found and fixed by this evolution — a horizontally-mismatched wrong cluster (`cay_0031_1805`) and a vertically-mismatched wrong cluster (`cay_0007_1805`, same XY as the true trunk but disjoint Z range). The XY-only and XY+Z bounding-box variants each fixed one case but not the other; the full KDTree-to-nearest-trajectory-point approach (adapted from the already-present-but-unused `01_clean_pointcloud.py`) fixes both classes at once, is robust to non-circular/irregular scan paths, and is axis-agnostic by construction (true 3D Euclidean distance — no "which column is up" decision at all).
4. `patch_trunk_isolation_up_axis.py` — **[NEW, Sep 2026]** fixes a second, independent, previously-unknown bug: `remove_ground_plane()`, `estimate_trunk_axis()`, and `crop_to_trunk_cylinder()` all hardcoded array column **2 (Z)** as the vertical axis, but this dataset's verified world frame has column **1 (Y)** as vertical (§6 gravity note). This broke ground-plane detection (real ground survived filtering) and corrupted the trunk-center estimate (mixed a true horizontal axis with the true height axis into one "radius" check) — reproduced and confirmed against real screenshots showing an "L-shaped" root-stub-plus-soil blob kept instead of the actual trunk. Fixed via the new shared `geometry_utils.py` (`UP_AXIS=1`), also imported by `06_slope_analysis.py` and `diagnostic_trunk_axis.py` so the convention can't silently diverge again. Independent of, and stacks with, patch 3 above (disjoint code regions — order of application doesn't matter).
5. `patch_trunk_isolation_slice_declutter.py` — **[NEW, Sep 2026]** adds `remove_off_axis_clusters_per_slice()`, called between the green filter and the 3D DBSCAN step. Fixes a case the existing 3D `keep_largest_cluster()` cannot: a real branch (or a second, separate nearby trunk) that is topologically fused to the target trunk through a contiguous vertical "neck," so it always ends up in the SAME 3D DBSCAN cluster no matter how small `eps` is set (confirmed on `cay_0007_1805` — sweeping eps 0.02→0.04 never split it off; see §12). Root-caused via a stage-by-stage replay: cutting the trunk into thin height slices and doing a small-eps 2D (X,Z) DBSCAN *within each slice independently* cleanly separates the branch into its own, smaller sub-blob in the height band where it exists (slices 11–18 of 40 on that scan, ~0.8m of a ~3.08m trunk, offset ~25–30cm from the main axis, 80–880 pts vs the trunk's own 1200–3700 pts there) — because the branch is NOT topologically continuous with the trunk within any single thin slice, only across the full 3D volume. Keeps only the largest-point-count blob per slice; slices with too few points to cluster reliably (`< min_points`) are left untouched (same "don't guess, only act on a real sparse signal" philosophy as the `04b_finalize_mesh.py` fix, item 8 below). Real data also **disproved** the initially-proposed alternative of picking the larger-*radius* blob instead of larger-*point-count*: in the 3 real disagreement cases found, the larger-radius blob was consistently the noisier, sparser one (fewer points, higher point-to-centroid coefficient of variation) — not a genuinely thicker trunk cross-section — so point-count was kept as the tie-break. `--no-slice-declutter` to disable. **Not yet re-validated beyond 1 scan.**
6. `patch_trunk_isolation_hue_green_filter.py` — **[NEW, Sep 2026]** adds a Hue+Saturation OR-condition to `remove_green_vegetation()` (`H ∈ [65°,150°] & S > 0.25`, the same formula already validated in `05_detect_lichen.py`'s `is_vegetation` check — lichen in this project's active detection path is white/pale, never green, so this cannot remove real lichen data, only true green vegetation/moss). Root cause (confirmed on `cay_0007_1805` after fixing item 5 above, real leftover green patches still visible in the user's own screenshots of `trunk_pointcloud.ply`): the old RGB-difference-only rule (`g>r+0.15 AND g>b+0.15`) removed only 151/90,328 pts (0.2%) — real measurement of the leftover green points showed their Hue (79° avg) and Saturation (0.53 avg) were clearly separated from bark (47°, 0.24 avg), but their `g-r` channel (0.059 avg) sat at barely a third of the 0.15 threshold, while `g-b` (0.200 avg) cleared it easily — the AND-combined RGB-diff rule was bottlenecked entirely on one channel. Lowering the RGB-diff threshold was tested and rejected: at 0.06 it caught only ~49% of the real green points at 82% precision; lower thresholds traded more recall for rapidly worsening false-positive rates on real bark (58.6% precision at 0.02). `--no-hue-green-filter` to disable (falls back to RGB-diff only). Confirmed on the same scan: green-filter removal jumped from 151 to 9,124 pts (10.1%), with the two large visible green patches from the screenshots gone. Residual: a few small greenish tufts remain faintly visible, still attached to the main DBSCAN cluster via a thin physical connection (only 58/76,032 pts were excluded as a separate cluster) — likely too small/thin to trigger either color or geometric criteria; not yet investigated further. **Not yet re-validated beyond 1 scan.**

7. `patch_trunk_isolation_adaptive_crop.py` — **[NEW, Sep 2026]** replaces the single-fixed-axis `crop_to_trunk_cylinder()` call in `isolate_trunk()` with `crop_to_trunk_cylinder_adaptive()`: every height slice gets its **own** center, tracked along the trunk's real path. Root cause (confirmed on `cay_0004_1805`): `estimate_trunk_axis()` takes one median (X,Z) over the top 60% of points, and a wide non-trunk structure near the base (root flare / soil, `r_med` up to 41cm there) dragged that median **22.6–29.5cm away** from the real trunk (which is only ~4–5cm in radius higher up) — comparable to the 0.3m crop radius itself, so roughly half of every trunk cross-section fell outside the crop and the output looked *sliced lengthwise*. Widening `--trunk-radius` was **disproved** as a fix: the offset, not the radius, was the problem, so a wider cylinder just admits more base debris on the far side. Algorithm: (a) wide bounding crop (0.8m) around the rough axis; (b) per-slice 2D (X,Z) DBSCAN for candidate blobs; (c) **seed** = the upper-60% slice whose largest blob's radius is closest to the median of those radii (avoids seeding on an outlier-size blob); (d) propagate up *and* down, each next slice picking the blob **nearest the previous slice's center** — continuity, deliberately *not* largest-point-count, because on `cay_0004` the wrong base blob has more points than the real trunk and point-count selection would re-commit the original bug; a slice with no blob within `--max-jump` (default 10cm) keeps the previous center unchanged rather than guessing; (e) final crop per point against **its own slice's** center. Validated on 5 scans before shipping: `cay_0004` went from a sliced sliver to a smooth 4.1–6.5cm-radius column tapering to 2.1cm at the top (35/40 slices tracked, the 5 base slices correctly *refusing* to jump to the 41cm debris blob), while `cay_0007`/`0010`/`0005`/`0009` changed by −0.4% to +12% in point count with no structural regression. Falls back to the old fixed crop automatically if there are too few points or no seed; `--no-adaptive-crop` to force the old path.
8. `patch_trunk_isolation_adaptive_seed_gate.py` — **[NEW, Sep 2026]** two guards for item 7, after `cay_0013_1805` failed hard (`trunk_pointcloud.ply` came out a shapeless 15,784-pt cloud). The user's hypothesis ("this trunk is much bigger than the others") was **disproved by measurement**: the real trunk is at (0.34, 0.11) with `r_med` 12.1cm — normal, and smaller than `cay_0007`'s 16.9cm which works fine. The actual cause: a **neighbouring tree** ~55–60cm away has *more points than the target trunk* in the 1.22–1.61m height band, and item 7's seed rule had no notion of which candidate belonged to the target tree, so it seeded on the neighbour, tracked it, coasted 21/40 slices and swept junk within 30cm of a frozen wrong center. Note the rough axis (0.245, −0.012) was ~15cm from the real trunk and ~55cm from the neighbour — i.e. it was pointing at the right tree all along; the algorithm simply stopped using it after the wide crop. Fix (a) **seed gate** (`--seed-max-offset`, default 0.40m): a seed candidate must lie within that distance of the rough axis. Threshold set from real measurements, not guesswork — `cay_0004`'s true trunk is at most 29.5cm from its own (biased) rough axis and must be kept; `cay_0013`'s neighbour is at least 55.5cm away and must be rejected. Fix (b) **coast sanity check** (`max_coast_ratio`, default 0.50): if more than half the data-bearing slices lost tracking, the whole tracking pass is considered failed and the function falls back to the old fixed crop with a warning instead of emitting garbage. Verified on 6 scans: `cay_0013`'s seed moved to the real trunk (`r_med` 11.4cm, matching the independent measurement), coast dropped 21/40 → 7/40, output 15,784 → 92,479 pts; the other five scans' seeds and point counts were **unchanged** (≤0.02% drift). Observed coast ratios across all 6: 5–25%, comfortably below the 50% limit, so the safety net does not misfire on healthy scans.

**`02_mesh_poisson_trunk.py`** (NEW script, pipeline step 4b) and **`03_recolor_mesh.py`** (step 5):
1. `02_mesh_poisson_trunk.py` — **[NEW, Sep 2026]** builds the trunk mesh with Poisson reconstruction from `trunk_pointcloud.ply` instead of taking the TSDF mesh. Root cause and the eleven disproved TSDF configurations are in §12 item 15. Normals are estimated then flipped **outward relative to each height slice's own axis** rather than by tangent-plane propagation, which is unreliable on a point shell measured at 2.7–5.6cm thick. Poisson always returns a closed surface, so the output is density-trimmed at the 5th percentile and clipped back to the point cloud's own height range (Poisson otherwise extrapolates caps past both ends), then reduced to the largest connected component. **`--depth` was chosen by measurement, not by eye**, against the cylinder area implied by the point cloud (`2π·r_med·h`) — the reference that matters because `05_detect_lichen.py` derives `total_cm2` from mesh triangle areas. Measured on 12 scans, area after the Taubin smoothing `04b_finalize_mesh.py` already applies: depth 6 gives 0.92–1.27× but meshes so sparse some scans fall below 1,000 vertices; **depth 7 gives 0.89–1.52×** with largest boundary loop 14–75 vertices and radius fidelity 0.98–1.12×; depth 8 gives 1.04–1.91×; depth 9 gives 1.16–3.10× because it follows the noise in the point shell and comes out crumpled. For comparison the TSDF mesh scores 0.35–2.89× with loops of 374–1,383 vertices. Note the "distance to nearest point" metric is **misleading here** — depth 9 scores best on it (0.7cm) precisely because it fits the noise, while depth 7's 3.9cm on rough scans just reflects the shell's thickness. `--depth` remains tunable per run.

3. `patch_poisson_ring_trim.py` — **[NEW, Sep 2026]** adds `slice_ring_gaps()` / `longest_closed_run()` / `closed_band_range()` and calls them in `process_scan()` **before** `orient_normals_outward()`, cropping an in-memory copy of the cloud (never `trunk_pointcloud.ply` on disk — it is still the colour source for step 5, the mask for step 6 and the label source for step 8). 4. `patch_poisson_flat_rims.py` — **[NEW, Sep 2026]** adds `_boundary_rims()` / `flatten_open_ends()`, called right after `keep_largest_component()`, cutting each open end back to where its boundary loop is genuinely planar. **This exists because item 3 alone was not enough, and counting boundary loops hid that.** After the ring trim `cay_0004` had exactly 2 loops — which reads as clean — but the top loop *spanned 21.7cm vertically* while the bottom spanned 0.0cm. Gravity is constant in the world frame, so the fix rotates each sample and averages the *results*. (c) **the real cause of "horizontal": a missing constant rotation between the CoreMotion device frame (`imu.csv`) and the ARKit camera frame (`odometry.csv` quaternions)** — the old code assumed they were the same ("Stray Scanner: camera frame ≈ device frame", its own comment). **The constant was solved from data, not guessed:** a consistency test (gravity must agree across samples) killed `R_i @ a_i` (scatter 65–81°, consistency 0.11–0.29) in favour of the `R.T` family (scatter 10–16°, 0.91–0.96); an independent look-direction test (the camera must point at the trunk, whose position is known from `trunk_pointcloud.ply`) confirmed `R` is camera→world, matching `pose_to_extrinsic()` in `02_pointcloud_and_mesh.py`, with the camera looking along **+Z** (3–6° error); Kabsch/Wahba then solved `C` in `g = R_i @ C @ a_i` with residual 2.9–4.3° and **the identical matrix on every scan** (the rival form `R.T @ C @ a` gave 61–78° — rejected). Finally the whole thing was re-solved for **both `C` and `g` from random initialisations with no ground truth at all**: 47 of 49 scans converged independently on `g = world −Y` (0.0–0.7°, median 0.1°) with that same `C` (0.1–1.3°). 2. `patch_pointcloud_skip_corrupt_step2.py` — same pattern for the file's *separate* internal TSDF-mesh loop (STEP 2 internal) — this is a distinct code path from `02_mesh_tsdf.py` and needed its own patch
3. `patch_pointcloud_sample_frame.py` — the "detect native resolution" step originally hardcoded to `poses[0]`; now tries frames in order until it finds one with both readable depth and rgb (handles corrupted frame 0)

**`05_detect_lichen.py`** (pipeline step 8) — applied in this order:
1. `patch_detect_lichen_diagnose.py` — prints vote-count histogram (mesh-transfer voting) — diagnostic only
2. `patch_detect_lichen_relax_threshold.py` — vote threshold `>=2` → `>=1` — **later shown to be a minor factor, not the main cause of over-detection (see item 7)**
3. `patch_detect_lichen_diagnose2.py` — separates raw-label-present vs post-brightness-filter vote counts — diagnostic only
4. `patch_detect_lichen_diagnose3.py` — prints bounding boxes of PCD / white-labeled points / mesh vertices — diagnostic only, but this is what caught the `cay_0031_1805` / `cay_0007_1805` spatial-mismatch bugs (see trunk isolation, above)
5. `patch_detect_lichen_burnout_filter.py` — excludes points with V≥0.95 & S≤0.08 ("sensor-clipped glare") from white classification — **measured effect was tiny (~0.1–0.7% of points); kept as a harmless defensive filter, not the real fix**
6. `patch_detect_lichen_diagnose4.py` — separates `local_white`-only vs `abs_white`-only vs both vote counts — diagnostic that identified the real root cause
7. `patch_detect_lichen_drop_absolute.py` — **[key fix]** removes `abs_white` (global absolute-brightness threshold) entirely; keeps only `local_white` (compares each point to its 40 nearest 3D neighbors). Confirmed via real data: `abs_white` alone contributed ~9% false-positive rate vs `local_white`'s ~1.7%, and this ~9–12% baseline noise rate was being amplified by neighbor-voting math into 74–79% "lichen coverage" on a tree very likely closer to a few percent in reality.
8. ~~`patch_detect_lichen_tune_local_contrast.py`~~ — **[CORRECTED Sep 20 2026: this was never actually applied.]** This entry used to claim the "medium bark" bucket (`bark_p20` ∈ [0.32, 0.45)) had been loosened to `v_sigma_k 0.7`, `v_sigma_base 0.03`, `req_s_drop 0.05`, from one measured lichen-vs-bark HSV sample. Verified against the file: [05_detect_lichen.py:188](05_detect_lichen.py#L188) still reads `1.0, 0.04, 0.08` — **the original values** — and no such patch script exists on disk. Same class of loss as `patch_trunk_isolation_kdtree_anchor.py` (item 3 of the trunk-isolation list), which also vanished and had to be rewritten from this file's own description. Here, though, nothing needs restoring: the tuning was explicitly flagged as calibrated from a single tree and single lighting condition, so its absence is the safer state. **All three bark buckets are at their original thresholds.** Do not re-apply without multi-tree data.
9. `patch_detect_lichen_summary_align.py` — **[NEW, Sep 2026]** fixes the `--batch` summary table attributing **the wrong scan's numbers to every row after the first failure**, and silently dropping the last N scans. `all_stats.append(r["stats"])` ran only on success and stored no scan name, while the table did `zip(dirs, all_stats)` — pairing all 51 scan directories against 46 results positionally. Caught in practice: the table printed `cay_0006_1805  11816 … 30.6` for a scan that has no `pointcloud.ply` and produced no stats at all, while the real `cay_0007_1805` row showed the next scan's figures. **The per-scan `lichen_stats.json` files were always correct** (each carries its own `"scan"` key) — only the corpus-level report was wrong, which is precisely what gets read when comparing trees. `lichen_summary.json` had the same defect in worse form: a bare list with no names, impossible to join back (grep-confirmed no in-repo readers before changing its shape to `[{"scan":…, "stats":…}]`). Fix stores `(name, stats)` pairs and iterates them directly. Note `05_detect_lichen_v2.py` carries the same pattern but is not in the active pipeline and was left alone.

**`run_full_pipeline.py`** (new orchestrator, not a patch of an original file, but itself was later patched):
- Adds a pre-flight `check_script_modules()` before each step (imports the modules that step needs in a throwaway subprocess) to fail fast with a clear message on a broken venv, instead of a deep traceback mid-step.
- Adds `env["PYTHONIOENCODING"]/PYTHONUTF8"]` to every subprocess call (see rules above).

## 6. Key Implementation Details

### Gravity vector

- `04_trim_mesh.py` and `05_detect_lichen.py` both call `estimate_gravity(dataset_path)`.
- **Per original docs:** reads `location.csv`, takes median of `gravity_x/y/z`, normalizes.
- **[VERIFIED this session]:** in the actual code read during debugging, `04_trim_mesh.py`'s gravity function is **hardcoded to `[0, -1, 0]`** with a comment claiming this is "always true for this dataset (verified via PCA on clean meshes)" — i.e. it does **not** dynamically read `location.csv`/IMU per-scan in the version examined. This is a documentation/behavior discrepancy that was **not resolved** — if `location.csv`-based dynamic gravity is expected, this needs re-auditing against the exact file version in use.
- `06_slope_analysis.py` reads `imu.csv` directly and rotates to world frame via `odometry.csv` quaternions. **[CORRECTED Sep 2026]** the original docs called this "the more trustworthy slope source"; measurement showed it was returning a **horizontal** gravity vector on every scan until `patch_slope_analysis_gravity_frame.py` (§5). Two facts worth keeping in mind here: **`imu.csv` is in units of g, not m/s²** (|a| median 0.996–1.001 across 49 scans), and the accelerometer's CoreMotion **device** frame is *not* the ARKit **camera** frame — they differ by the constant `DEVICE_TO_CAMERA` rotation now defined in that file. Since ARKit uses gravity world-alignment, the correct answer is world −Y to within 0.63° on all 49 scans; treat any larger deviation as a bug signal, not as terrain.

### TSDF parameters

- Library: `open3d.pipelines.integration.ScalableTSDFVolume`
- **[RESOLVED Sep 2026]** `voxel_size=0.005m` (CLI default, confirmed in `tsdf_summary.json`) and **`sdf_trunc=0.05`** — the earlier "0.02" in these docs was wrong. `sdf_trunc` has no CLI flag and is never passed by any caller, so `process_scan()`'s default of 0.05 is always what runs. Sweeping it 0.010–0.16 changes the hole count inside the trunk hardly at all while inflating the mesh radius up to 2.44× — see §12 item 15
- Server value per original docs: `voxel_size=0.008m` via `TSDF_VOXEL_SIZE` env var — unverified this session
- Depth: uint16 PNG (mm) → float32 (m); confidence filter `conf < 1` zeroed (per original docs, not re-verified)

### HSV lichen detection

Two functions exist in `05_detect_lichen.py`:

1. **`classify_lichen(rgb)`** — legacy, absolute-threshold, has real white/green distinction:
   - `is_vegetation = (H∈[65°,150°]) & (S>0.25)`
   - `white = (V∈[0.70,0.97]) & (S<0.25) & ~is_vegetation`
   - `green = (H∈[60°,155°]) & (S≥0.25) & (V∈[0.30,0.92]) & ~white`
   - **[VERIFIED] Only called as a fallback** when `trunk_pointcloud.ply` doesn't exist — not the active path for this dataset (it always exists).

2. **`classify_lichen_local_contrast(pts, cols, k=40)`** — **[ACTIVE]**, the function that actually determines results:
   - `is_veg = (H∈[65°,150°]) & (S>0.25)` — used **only to exclude**, never to positively identify lichen
   - `local_white`: point must be brighter than its 40 nearest 3D neighbors by `v_thr`, AND less saturated than them by `req_s_drop`, AND `S<0.42`, AND not `is_veg`
   - `abs_white`: global-threshold variant — **[REMOVED, patch 7 in §5]**, confirmed root cause of severe over-detection
   - Final: `white = local_white & ~is_burnout` (label=2); everything else defaults to label=0 (bark). **`classify_lichen_local_contrast` never emits label=1 (green) — "green lichen" does not exist as a concept in the active detection path**, despite `green_lichen_cm2` still being a field in the output JSON (always 0.0 by construction).
   - Adaptive bark-type buckets (`bark_p20 = percentile(V, 20)`), original 3-tier table for reference (values for the "medium" row are now superseded per patch 8 in §5):

   | Bark type | Condition | v_sigma_k | v_sigma_base | req_s_drop |
   |---|---|---|---|---|
   | Dark | bark_p20 < 0.32 | 0.8 | 0.03 | 0.03 |
   | Medium | 0.32–0.45 | ~~1.0~~ **0.7** | ~~0.04~~ **0.03** | ~~0.08~~ **0.05** |
   | Light | ≥ 0.45 | 1.2 | 0.05 | 0.08 |

### Color science finding (important, cross-checked against real photos)

Direct pixel measurement of confirmed-by-eye lichen patches vs adjacent bark (multiple images, multiple trees) showed **Hue is not a usable discriminator**: lichen and bark Hue values cluster in the same ~30–38° (orange-brown) range regardless of the patch's visually "grayish-green" appearance to the human eye. **Only relative brightness (V) and relative saturation (S), compared locally, carry any real signal** — and even that signal is of *moderate*, not dramatic, magnitude, and was inconsistent in direction across some manually-cropped samples (possibly due to motion blur / imprecise 2D crop selection vs the pipeline's actual 3D-neighbor comparison). **Conclusion: a pure-color (Hue-based) reclassification approach was evaluated and rejected** — it would remove the only working signal without adding a new one, given bark and lichen occupy the same hue.

## 11. Common Issues (merged)

- **ffmpeg not found:** install `imageio-ffmpeg` (pip) or ensure `ffmpeg` on system PATH (`sudo apt install ffmpeg` / `brew install ffmpeg` per original docs). If the bundled `imageio-ffmpeg` binary crashes with `0xC0000005` on a specific video, try `-threads 1` or a different ffmpeg build (gyan.dev vs BtbN) — some builds tolerate corrupt/truncated MP4 (missing `moov` atom, bad HEVC bitstream) better than others. A truncated-MP4 (`moov atom not found`) can sometimes be recovered with `untrunc` using a known-good file from the *same device/app/settings* as a reference.
- **open3d TSDF OOM / crash (`STATUS_STACK_BUFFER_OVERRUN`, `STATUS_ACCESS_VIOLATION`):** almost always a symptom of (a) corrupted input data (garbage coordinates, corrupt depth/rgb frames) or (b) genuine RAM exhaustion on point clouds >5–10M points on an 8GB machine. See §5 patch chain for both fixes; also consider raising `TSDF_VOXEL_SIZE`/reducing `max_depth` per original docs.
- **DBH = null (per original docs):** fewer than 20 points at z=1.2–1.4m — scan too sparse at breast height; re-scan. Unverified this session; not encountered.
- **Gravity fallback used:** per original docs, means `location.csv` missing → hardcoded axis. **[VERIFIED] contradicted by actual code inspection this session** — `04_trim_mesh.py`'s gravity function was hardcoded regardless of `location.csv` presence in the version read. Re-audit before trusting either claim.
- **Wind data unavailable (per original docs):** Open-Meteo API unreachable from Railway — check network egress settings. Unverified this session.
- **Environment corruption (pip internals, DLLs, point clouds, images) with no obvious cause:** if working from a USB external drive, suspect the drive itself first (`chkdsk /f /r`, disable USB selective suspend, migrate to an internal drive) before assuming RAM or software bugs — this cost significant debugging time in this session before being correctly diagnosed.
- **Windows console `UnicodeEncodeError`/`UnicodeDecodeError` on Vietnamese paths or requirements.txt:** ensure all patch/script files are pure ASCII, and pass `PYTHONIOENCODING=utf-8`/`PYTHONUTF8=1` to any subprocess.
- **[NEW, Sep 20 2026] `MemoryError` in step 2 on a long scan.** `create_rgbd_pointcloud()` used to hold every frame before downsampling once; fixed by `ACCUM_MAX_PTS` (§5). If it recurs, lower `--accum-max-pts`, and note the floor is the final cloud size (~14M points ≈ 0.7 GB, doubled during the last downsample). Closing the editor/browser frees several GB and is the fastest workaround.
- **[NEW, Sep 20 2026 — SOLVED] `moov atom not found` — the recording was interrupted, the file is not corrupted by the disk.** Hit on `cay_0006_1805` and `cay_0022_1805`. Their `rgb.mp4` holds `ftyp` + `wide` + an `mdat` whose declared size is **0**, with **no `moov`**: the payload is all there but the index, written last, never was. That is a capture cut short (battery, app killed), not §4's drive corruption — **do not go looking for a disk fault**. `camera_matrix.csv` is written at session end too, so it may be missing on the same scans. **Recovered in-repo by `recover_truncated_mp4.py`** (no `untrunc` needed): the payload is HEVC NAL units with 4-byte length prefixes, and only the codec configuration is lost, so it is borrowed from a healthy scan's `hvcC` box and the prefixes converted to Annex-B start codes. Both scans read to the exact end without losing sync, giving 2,812 and 1,724 frames against 2,850 and 1,728 depth images — an independent check on the parse. Run it, then `run_full_pipeline.py <scan> --from-step 2`.
- **[NEW, Sep 2026] Running one scan wiped the corpus summary file.** `--scan X` goes through the same `run_batch()` as `--all`, just with the directory list filtered to one — and then overwrote `<step>_summary.json` with that single row. Found *after* it had already fired: `recolor`/`trim`/`finalize`/`lichen_summary.json` were each down to **1 of 46** scans. Fixed in `pipeline_io.py` (§5); rows are now merged. **Diagnose an old one with** `len(json.load(open(p))["results"])` — a summary far smaller than the scan count is this bug, not a failed batch. The per-scan `output/*.json` files were never affected, so re-running the step rebuilds the summary.
- **[NEW, Sep 2026] Steps 5–8 default to the wrong raw-data directory.** `03_recolor_mesh.py`, `04_trim_mesh.py`, `04b_finalize_mesh.py` and `05_detect_lichen.py` set `RAW_DATA_DIR = <repo>/Raw_data`, while `02_mesh_poisson_trunk.py` hardcodes `D:\Backup\Thucdia-18May2026`. Running the four without `--raw-data` dies instantly with `FileNotFoundError: ...\Lichen_project\Raw_data`. It stays hidden because `run_full_pipeline.py` always passes `--raw-data` explicitly. **Always pass `--raw-data` when driving these four by hand.**
- **[NEW, Sep 2026] `git` silently ignoring the entire repository — PowerShell wrote UTF-16 into a UTF-8 file.** `git status` looked clean, `git add` appeared to work, and nothing was ever committed. Cause: `.gitignore` had two lines appended with PowerShell 5.1's `>` / `Out-File`, which default to **UTF-16LE**. The bytes landed as `* \0 . \0 z \0 i \0 p \0 …`; git stops at the first `\0`, so the intended `*.zip` became a bare **`*`** and matched every path. **Diagnose with** `git check-ignore -v <any-file>` (it names the offending file and line — here `.gitignore:29:*`) and `od -c .gitignore` (look for `\0` bytes interleaved with ASCII). **Avoid by** never using `>` or `Out-File` to write a text file other tools read — use the editor/Write tool, or `Out-File -Encoding utf8` explicitly; `Set-Content`/`Add-Content` default to ANSI and are equally unsafe. This hid every change made between Aug and Sep 2026 from version control; the repository had to be rebuilt (see the note at the top of §5). The same class of bug can corrupt `requirements.txt`, `.gitattributes` or any config the same way.
- **`git fsck` reporting pack checksum mismatch / objects that will not inflate:** the pack is corrupt and `repack` cannot fix it (the damage is below the object layer). If the remote is reachable, re-clone. If not — as happened here — back up the working tree, rename `.git` aside rather than deleting it, `git init` fresh, and commit the tree as a new baseline. Expect this on any machine with the §4 drive history.

13. **[NEW, Sep 2026 — MODELLING QUESTION, NOT A CODE BUG] `terrain_slope_deg` does not measure terrain slope; it measures how far the trunk leans from vertical, and nothing in the raw data can validate it.** This only became visible once item 12 fixed gravity. ARKit uses gravity world-alignment, so world −Y *is* gravity (confirmed: 0.63° worst case over 49 scans). `compute_slope_direction()` therefore reduces to: `slope_down` = the direction the trunk leans, and `terrain_slope_deg` = the trunk's tilt (1.3–6.0° on real scans). That equals the terrain slope **only if trees grow perpendicular to the ground**, which they generally do not — trees grow vertically regardless of slope. So `n_upslope_pts`/`n_downslope_pts` and `trunk_labeled.ply` currently split each trunk by **which side it leans toward**, not by which side faces uphill. Two further findings: (a) **there is no terrain-slope ground truth anywhere in the raw data** — `location.csv`'s `slope_degrees` field is the **phone's own inclination** (median 78–84°, matching the ~86° measured straight from the IMU), not the ground's; the only other terrain signal is GPS altitude, at 10.3m stated accuracy. (b) the lean direction itself is **not** noise-limited — bootstrap-resampling the trunk cloud moves the lean azimuth by only 0.5–1.9° (p90), flipping ≤0.7% of points between sides — so the number is precise; the open question is whether it means what the field name claims. **Decide what this deliverable should actually measure before publishing any upslope/downslope statistic.**

This is the same amplification already suspected in item 3 ("~9–12% baseline noise rate amplified by neighbor-voting math into 74–79% coverage"), now measured directly rather than inferred. **Consequence: every lichen percentage in the corpus is mesh-resolution-dependent and inflated by roughly 4–6× relative to the point data.** **[UPDATE Sep 20 2026 — measured again after the depth-8 rebuild, and the gate set for it failed.]** The point-level reference reproduced exactly (0.66 / 3.24 / 5.93%), so the comparison is like-for-like. Amplification against that reference moved **5.8× → 3.9×** on `cay_0005` and **5.2× → 4.5×** on `cay_0007`, but **3.0× → 3.6×** on `cay_0004` — better on two trees, worse on one, mean 4.7× → 4.0×. In reported terms the three moved 18.7 → 12.5%, 30.6 → 26.7% and 2.0 → 2.4%. **The acceptance gate written into the plan ("reported percentage must not shift by more than ~2 points") was broken by two of the three trees**, and that gate was badly chosen: it gated on a quantity this very item documents as mesh-resolution-dependent, so there was never a stable value for it to hold. The direction is not even uniform, which is itself evidence the reported number tracks mesh resolution more than it tracks lichen. **Every lichen figure produced before Sep 20 2026 is stale, and the new ones are no more publishable — merely less inflated on average.** Nothing has been changed in the detection path — the ≥1 threshold was set deliberately by an earlier patch and reverting it is a scientific decision, not a bug fix. Resolve this before publishing any coverage number, and decide whether the deliverable should be computed on the point cloud (resolution-independent) rather than on mesh triangles at all.

19. **[NEW, Sep 21 2026 — MEASURED] The active lichen detector has an F1 of 0.5%, and a label-fitted replacement reaches 42.8% on held-out data.** This is the first accuracy number in the project's history that was measured rather than inherited. Ground truth: 12 frames of `cay_0004_1805`, chosen by greedy max-coverage so they see 179/192 grid cells (93% of the trunk) rather than clustering in one stretch, hand-painted magenta by the user, projected back onto `trunk_pointcloud.ply` by `annotate_lichen.py read`. **3,271 of 18,284 points that at least one annotated frame saw are lichen — 17.9%. The pipeline reports 0.7%.**

    | on the held-out half | precision | recall | F1 |
    |---|---|---|---|
    | `05_detect_lichen.py` as shipped | 6.3% | 0.2% | **0.5%** |
    | one threshold on aggregated `a*` | 30.1% | 63.7% | 40.9% |
    | logistic, illumination-normalised (`--features illum`, default) | 36.1% | 52.4% | **42.8%** |
    | logistic, adding raw colour (`--features all`) | 40.8% | 54.3% | 46.6% |

    **The validation split is by grid cell in a checkerboard, not by point.** Two neighbouring points almost always share a label, so a random point split scores the model on data it effectively saw; the checkerboard keeps whole (height band × angular sector) cells on one side or the other. It is balanced by construction here — 17.6% lichen in the calibration half, 18.2% in the held-out half — and the model scores **42.8% held out against 42.7% on the calibration half**, i.e. there is no overfitting to detect.

    **The new model's features are the ones §12 item 18 identified, not new science:** L/a/b aggregated from the raw frames (not from `trunk_pointcloud.ply`, whose colours are averaged over every viewing angle including grazing and back-facing), counting only points whose surface normal faces the camera, then the angle-residual of each channel plus 3D local contrast. Best single feature is `a*` at AUC 0.708.

    **The trap this could have fallen into, and the check that is now built in.** The current detector fires on the shaded side (brightness vs reported lichen rate, r = −0.75). A model fitted on one tree can learn the same confound in reverse, and would then score well here and fail on a tree lit from another direction. `fit` therefore always prints the per-sector table and both correlations. On this tree the true lichen rate genuinely does correlate with brightness (**r = +0.56**) and the default model matches it (**+0.59**) — it is tracking the lichen, not the light. The `--features all` variant correlates **+0.84**, buying 4 points of F1 by riding the illumination, which is why `illum` is the default despite scoring lower.

    **Two caveats on the ground truth itself.** (a) The annotator can only paint lichen they can *see*, and lichen on the dark side of the trunk is harder to see in a photo — so part of that +0.56 may be annotation bias rather than biology. (b) It is one tree and one sun direction. **Nothing here is usable on the corpus yet**, and none of it touches the shipped pipeline: `05_detect_lichen.py` is unchanged and `model.json` is not read by anything. Next step is labelling several trees with different lighting and cross-checking between them, before deciding whether to replace the detection path.

    | `cay_0007_1805` | 38° | 44,407 | 26.7% |
    | `cay_0036_1805` | 270° | 21,045 | 15.4% |

    | held-out tree | precision | recall | F1 (final) | F1 (item 19 features) | shipped detector |

    | `cay_0007` | 44.9% | 58.1% | **50.6%** | 39.5% | 10.5% |
    | `cay_0036` | 20.7% | 60.5% | **30.8%** | 27.8% | 17.4% |

    **The model does not ride the illumination.** On every held-out tree its correlation with sector brightness is *lower* than the truth's: +0.22 vs +0.55, +0.57 vs +0.90, +0.43 vs +0.79. Compare the shipped detector at r = −0.75.

    **Three feature families were tried; two failed, and the failures are the more useful result.**
    - **Geometric roughness — no signal whatsoever.** Local-PCA surface variation and plane-fit residual at k=20 and k=60, plus radial deviation from the local cylinder: **AUC 0.478–0.525** across three trees, and adding them moved mean F1 by **0.0 points**. The intuition that a lichen crust reads as a flatter surface than ridged bark is **not supported by this geometry** — plausibly because the point cloud is a 2.7–5.6cm-thick shell (§12 item 15) whose own noise exceeds bark relief. Not shipped.
    - **Image texture — real but redundant, and expensive.** Local standard deviation of L at 7/15/31-pixel windows (≈2/4/9mm on the trunk), divided by local brightness so it measures relative contrast rather than brightness. **AUC 0.54–0.60**, with the sign saying lichen is the *flatter* surface — so the hypothesis that failed in the geometry does hold in the image. But once normal-aware contrast is present it adds **nothing** (41.3% either way), and collecting it costs a **second full pass over every frame** (~7 min/scan). Not shipped. **Recorded here so nobody pays for that pass again.**
    - **What worked was mostly a removal.** `ra`,`rb` alone — the two chroma angle-residuals, no lightness anywhere — score **39.1%**, already above the item-19 nine-feature set's 35.1%. Putting `rL` back **drops it to 37.9%**. Lightness carries more information about the sun than about lichen; this is the §12 item 18 trap again, subtler than the shipped detector's version but the same mechanism.

    **The one genuine addition is `_normal_contrast()`:** local contrast computed only over neighbours whose surface normal points the same way (dot ≥ 0.90), at k=300 and k=1000. Ordinary 3D local contrast at large k **wraps around a 4–12cm trunk** and compares faces under completely different light. Filtering by normal keeps the comparison inside one face, so neighbours differ mainly in *height*. This takes 39.1% → 41.3%. It is chunked (4,000 points at a time) because k=1000 over 56k points would otherwise need ~1.8 GB on an 8 GB machine.

    **Final set: `FEATURES_ILLUM = ["ra", "rb", "nL300", "na300", "nL1000", "na1000"]`.**

    **Selection bias, stated plainly:** about twenty feature sets were scored on the same three trees, so 41.3% is optimistically biased. What makes it credible is that **the neighbourhood is a plateau, not a spike** — `ra` alone + normal-aware 41.6%, +`lcL` 41.2%, k=300 only 40.7%, k=1000 only 40.1%, `ra`,`rb` only 39.1%. The only sharp drop is adding `rL` (37.9%). **Choosing precisely within that plateau does not matter; excluding lightness does.**

The gain since then came from features, not data.     **The brightness correlation in the labels is neither annotation bias nor biology — it is [SELECTION]. This entry previously offered two readings — real biology, or the annotator under-painting the shaded side. **The user supplied a third, and it is the right one: when choosing which tree to film, the operator mostly picks trees that visibly have more lichen on the sunlit side.** The correlation is therefore built into the sample before any photograph is taken.

    **(a) Good for the detector — and measured.** Annotation bias is no longer the leading explanation, so the labels are not presumed to be systematically missing shaded-side lichen. More usefully, the leave-one-out prediction was scored separately on the lit and shaded halves of each trunk (lit half = the angular sectors whose mean L is above the trunk's own median):

    | scan | half | precision | true lichen | **lift** | F1 |
    |---|---|---|---|---|---|
    | `cay_0004` | lit | 36.7% | 21.2% | **1.73** | 47.0% |
    | `cay_0004` | shaded | 25.5% | 14.5% | **1.76** | 36.8% |
    | `cay_0007` | lit | 55.8% | 34.5% | **1.62** | 57.3% |
    | `cay_0007` | shaded | 29.3% | 16.9% | **1.73** | 38.4% |
    | `cay_0036` | lit | 26.7% | 19.8% | **1.35** | 37.7% |

    F1 does fall on the shaded half of every tree — but **lift (precision ÷ base rate) is identical: 1.57 lit, 1.57 shaded.** The detector discriminates exactly as well on the dark side; F1 drops only because there is genuinely less lichen there to find, and precision tracks prevalence. **Read lift, not F1, when comparing regions with different base rates** — the raw F1 column alone would have supported a conclusion the data does not.

    **(b) Bad for the science, and this is the serious half.** If trees are chosen *because* their sunlit side carries lichen, then **this corpus cannot be used to ask which side lichen prefers** — the answer was fixed by the sampling. That is a second, completely independent problem on top of §12 item 13 (which says the upslope/downslope split measures trunk lean, not terrain aspect). Item 13 says the quantity is mislabelled; this says **the sample is selected on the outcome**. Both must be resolved before any orientation statistic is published, and no re-run of `06_slope_analysis.py` touches either.

    **It also sharpens why lightness is excluded from `FEATURES_ILLUM`.** A model that used brightness would score well on this corpus by learning the *selection protocol*, then fail on any tree chosen some other way — for instance a monitoring re-scan, or a randomly sampled tree. The exclusion was justified above on measured F1; under selection bias it is also the only choice that survives a change of sampling.

    **What would actually answer the orientation question:** a subset of trees chosen **without looking at lichen at all** — random, or every n-th tree on a transect. Until such a subset exists, the corpus supports "how much lichen is on this tree" but not "which side lichen favours".

    **Still nothing in the pipeline has changed.** `05_detect_lichen.py` is untouched; `annotate_lichen.py apply` writes `trunk_mesh_detected_CHEO.ply` beside the pipeline's own output for visual comparison, and nothing reads it. Point-level coverage from the cross-fitted model reads 34.7% on `cay_0007` (hand-labelled 26.7%) and 44.2% on `cay_0036` (15.4%) — **the model over-detects, by 1.3× and 2.9×**, which is what precision 45% / 21% implies.

21. **[NEW, Sep 24 2026 — SERIOUS, NOT FIXED] The label-fitted detector locates lichen but cannot measure how much of it there is. Its per-tree total is anti-correlated with the hand labels (r = −0.90 on three trees), and the corpus-wide spread is implausibly narrow.** Found by running `annotate_lichen.py apply --all` over all 49 scans (51 minutes, 49/49 OK) and reading the table:

    ```
    49 scans   lowest 30.4%   highest 49.1%   median 40.8%   std 4.1
    ```

    Lichen on real trees cannot be that uniform, and `cay_0003_1805` — the known-broken capture whose whole mesh is 972 cm² — reads **43.6%**, mid-table. Against the three trees that have hand labels:

    | scan | hand-labelled | detector | ratio |
    |---|---|---|---|
    | `cay_0007` | **26.7%** | 34.7% | 1.30× |
    | `cay_0004` | 17.9% | 38.3% | 2.14× |
    | `cay_0036` | **15.4%** | **44.2%** | 2.87× |

    **The ranking is exactly inverted** — the tree with the most lichen reads lowest. Pearson r = **−0.90** (n = 3, so not conclusive on its own; see below).

    **Mechanism, measured.** The logistic score's mean is nearly identical on every tree (0.457 / 0.456 / 0.468) and the fixed threshold lands at the **56th–64th percentile** of each tree's own score distribution. So the detector selects a near-constant fraction of points regardless of what is on the tree. The cause is in the design: **all six features in `FEATURES_ILLUM` are relative** — residuals from that tree's own per-sector medians, and same-normal local contrast. That is what removes the illumination (§12 item 20), and it also removes the level, by construction.

    **A secondary mechanism was tested and only half-confirmed.** Lichen contaminates the very median used to measure it: the shift between "median over all points" and "median over hand-labelled bark only" scales with lichen fraction (−0.565 / −0.231 / +0.100 for 26.7 / 17.9 / 15.4%). Real, but **not the main cause** — the remaining a\* gap between lichen and the contaminated median is still *largest* on the high-lichen tree (−1.765 vs −0.581), so contamination does not explain the inversion.

    **The obvious fix was tried and disproved before asking the user for more labels.** Adding an absolute (non-recentred) feature back:

    | feature set | F1 | 0007 (26.7%) | 0004 (17.9%) | 0036 (15.4%) | level r |
    |---|---|---|---|---|---|
    | current, all relative | **41.3%** | 34.7% | 38.3% | 44.2% | −0.90 |
    | + absolute `a` | 36.6% | 23.6% | 32.5% | 39.7% | −0.97 |
    | + absolute `b` | 37.7% | 32.1% | **60.6%** | 27.2% | −0.17 |
    | + absolute `a`,`b` | 34.9% | 26.6% | 58.2% | 22.6% | −0.21 |
    | + absolute `L` | 39.1% | 31.3% | 42.3% | 41.2% | −0.95 |

    Absolute features **do** break the constancy (spread widens from 10 points to 33) but **none produces a positive level correlation**, and every one costs 2–7 points of F1. The total goes from uniformly meaningless to variably meaningless — it starts tracking each scan's bark colour and exposure, which is exactly why those features were excluded in the first place.

    **What this says about the method, and it is the important part.** §12 item 20's feature selection was scored on **within-tree F1** — how well the detector localises lichen on a trunk it has never seen. That metric is **blind to the per-tree total**, because F1 is computed per tree against that tree's own labels. The per-tree total is the project's actual deliverable, and it was never in the objective. **F1 41.3% remains valid for what it measures: where lichen is on a trunk.** It says nothing about how much.

    **Consequence: `05_detect_lichen.py` must not be replaced with this model yet.** Doing so would produce a corpus where all 49 trees read ~40% — precise-looking and meaningless, which is the same failure as the retired "~70%" claim, only newer.

    **Two things are needed and neither is more of the same.** (a) **Settle whether the anti-correlation is real.** n = 3 gives a 1-in-6 chance of a fully inverted ranking by luck; the 7-tree evaluation sample (§ below) makes it decidable. (b) **Find a route to the level that does not go through the same threshold.** Options not yet tried: calibrating predicted→true coverage as a separate regression once ≥10 trees are labelled; estimating coverage from the score distribution's shape rather than from a count above a threshold; or raising precision (currently 31–45%), since at a fixed ~40% selected fraction the reported total is dominated by false positives whose rate has nothing to do with lichen.

    **[Sep 24 2026] Estimating the total from the *shape* of the score distribution instead of counting above a threshold — four methods, all failed.** Scored by leave-one-tree-out on the three labelled trees:

    | method | r with truth | mean abs error |
    |---|---|---|
    | raw count above threshold | −0.86 | 19.2 pp |
    | adjusted count, `(q−FPR)/(TPR−FPR)` | −0.10 | 16.1 pp |
    | mixture fit to the score CDF | −0.42 | **10.4 pp** |
    | EM prior adjustment (Saerens et al.), raw | *degenerate* | 80.0 pp |
    | EM after isotonic calibration | −0.01 | 13.3 pp |

    **None reaches a positive correlation.** Three details worth keeping: (a) the adjusted count removes most of the anti-correlation (−0.86 → −0.10), confirming the inversion is largely an FPR artefact of the fixed-fraction threshold rather than something intrinsic; (b) raw EM **saturates at exactly 100.0% on all three trees**, so the +0.80 correlation it appears to score is computed on identical values and is meaningless — the posteriors are badly miscalibrated, and isotonic calibration fixes the saturation but not the correlation; (c) CDF matching is closest in absolute terms and gets two of three trees roughly right (17.9→14.6, 26.7→22.0) but misses the third by 23 pp, **and its fit residual is *lowest* on exactly that tree** (residual-vs-error correlation −0.59). It fails silently, which is the worst property an estimator can have.

    **A blur hypothesis was raised, pursued, and then killed by the annotator — twice over.** Every method reads `cay_0036` at 38–45% against a hand label of 15.4%, and that scan measures far lower Laplacian sharpness than the others (annotated frames 94 vs 243 and 364; whole-scan median 67 with 10 frames above 200, against `cay_0007`'s median 188 with 331). Two explanations were tested. **(a) Blur creating false colour contrast in the detector — disproved by measurement:** re-aggregating from frames above 150 (2.5× stricter) moves the reading only 44.2% → 42.8%. **(b) The annotator under-painting because boundaries were unreadable — disproved by the annotator**, who reports `cay_0036` was not hard to read and some of its frames were *easier* than other trees'. **Conclusion: Laplacian variance is not a proxy for human readability.** It measures high-frequency energy, which a smooth, evenly-lit, low-contrast trunk lacks even when perfectly in focus. `pick --min-sharp` was added during this episode and is kept as a tool, but the three trees re-exported with it were **reverted to the max-coverage selection** (back to 56–58% grid coverage), because the coverage was traded away for a benefit that does not exist. **Do not use sharpness to screen frames or scans without checking against a human first.**

    **[Sep 25 2026] The over-count is fully explained by per-tree signal strength — and that strength cannot be measured without labels, which is the actual blocker.**

    | scan | truth | detector | over-count | a\* gap lichen↔bark | sd(`ra`) | IQR(`ra`) |
    |---|---|---|---|---|---|---|
    | `cay_0007` | 26.7% | 34.7% | **1.30×** | **1.765** | 3.193 | 3.447 |
    | `cay_0004` | 17.9% | 38.3% | **2.14×** | **1.008** | 2.021 | 2.238 |
    | `cay_0036` | 15.4% | 44.2% | **2.87×** | **0.581** | 3.014 | 3.442 |

    The a\* gap — the median chroma difference between hand-labelled lichen and bark — correlates **−0.99** with the over-count factor. The mechanism is coherent: where lichen and bark differ by 1.765 the detector separates them and over-reads by 1.3×; where they differ by 0.581 it cannot, and falls back on marking its default ~40%.

    **Four label-free proxies for that gap were declared in advance and all failed:** sd(`ra`) −0.18, IQR(`ra`) −0.04, sd(score) +0.22, IQR(score) +0.37. The reason is visible in the table: `cay_0036`'s `ra` spread (3.014) is nearly `cay_0007`'s (3.193), because **total feature spread is dominated by within-bark variation, which is similar across trees. The between-class part is the only informative component and it is invisible without labels for that tree.**

    **So the per-tree total cannot be corrected by any route tried so far without labelling the tree being measured, which defeats the purpose.** What this approach delivers on current evidence is a *map* of where lichen sits on a trunk (F1 41.3%), not a *quantity*. **The one route not yet tried, and the one the 7-tree sample makes possible: a tree-level regression** — fit lichen % directly from a handful of tree-level summary statistics over ≥10 labelled trees, rather than deriving it by counting classified points. Ten points and two or three predictors is very small data, but it targets the deliverable directly instead of inheriting a per-point threshold's behaviour.
